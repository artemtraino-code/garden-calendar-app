# Garden Calendar App Blueprint

## Назначение

`garden-calendar-app` — отдельное локальное приложение для планирования и учета садово-огородных работ.  
Оно не связано с `seeds.dp.ua`, WordPress или WooCommerce.

Цель следующего этапа — перестроить текущий прототип в более собранное приложение, не теряя уже согласованную механику.

## Главный принцип

Единый источник данных — настройки приложения.

Все формы и все пользовательские сценарии должны опираться только на эти справочники:

- группы;
- культуры;
- работы;
- препараты.

Никакие скрытые тестовые списки, временные категории или локальные fallback-значения не должны участвовать в UI отдельно от настроек.

## Сущности

### 1. Группы

Примеры:

- Цветы
- Овощи
- Бобовые
- Деревья

Группа:

- имеет название;
- может иметь иконку;
- содержит несколько культур.

### 2. Культуры

Примеры:

- Петунии
- Розы
- Томаты и перцы

Культура:

- имеет название;
- может иметь иконку;
- может быть привязана к одной или нескольким группам.

### 3. Работы

Примеры:

- Посадка
- Полив
- Обработка
- Подкормка

Работа:

- имеет название;
- может иметь иконку;
- используется как шаблон при создании заданий.

### 4. Препараты

Препарат:

- имеет название;
- короткое описание назначения;
- дозировку;
- срок ожидания;
- описание;
- локальную картинку.

## Настройки

Верхний интерфейс приложения должен иметь только:

- `График работ`
- `Настройки`

Внутри `Настроек` должны жить вкладки:

- `Группы и культуры`
- `Работы`
- `Препараты`

Требование:

- окно настроек фиксированного размера;
- переключение вкладок не меняет габариты окна;
- все справочники редактируются только здесь.

## Единый multi-picker

Для всех множественных выборов используется один и тот же паттерн:

- dropdown;
- поиск;
- чекбоксы;
- `Выбрать все`;
- выбранные элементы дублируются chips-плашками;
- dropdown не схлопывается после одного клика;
- скролл списка не прыгает вверх после выбора.

Этот паттерн должен использоваться везде одинаково:

- группы в задании;
- культуры в задании;
- работы в задании;
- препараты в задании;
- культуры внутри настройки группы;
- группы внутри настройки культуры.

## Единая форма задания

`Новое задание` и `Редактировать` должны быть одним и тем же шаблоном формы.

Структура:

1. Статус
2. Группа
3. Культура
4. Работа
5. Дата
6. График
7. Препараты
8. Заметка

### Статусы

Системные статусы:

- `planned` -> `Запланировано`
- `done` -> `Выполнено`
- `missed` -> `Пропущено`

`Пропущено` — отдельный системный статус, а не вычисление только для цвета.

Он должен участвовать в:

- карточках ленты;
- редактировании;
- календарных плитках;
- счетчиках;
- логике фильтрации/навигации.

## График повторений

Поддерживаемые режимы:

1. `Не повторять`
2. `Повторить один раз`
3. `Повторить через`
4. `Повторять каждые`

### Правила

#### Не повторять

Следующее задание не создается.

#### Повторить один раз

Создается только одно следующее задание.

#### Повторить через N дней

Создается одно следующее задание через `N` дней.  
В заметке нового задания должен появляться префикс:

`Повтор работ от <дата>.`

#### Повторять каждые N дней

Следующее задание каждый раз должно ссылаться не на первую исходную дату, а на последнюю фактически выполненную работу.

Пример:

- 10 мая выполнено;
- следующее 17 мая;
- следующее 24 мая;
- заметка на 24 мая должна ссылаться на 17 мая, а не на 10 мая.

## Повтор из выполненной карточки

В карточке со статусом `Выполнено` в окне редактирования должны быть действия:

- `Удалить`
- `Повторить`

`Повторить`:

- закрывает окно выполненной записи;
- открывает новое задание;
- подставляет те же группы, культуры, работы, препараты и заметку;
- меняет статус на `Запланировано`;
- дописывает в заметку:

`Повтор работ от <дата выполнения>.`

## Карточка ленты

Текущая целевая структура карточки:

### Левая колонка

- дата;
- работа;
- культура.

### Правая колонка

- препараты;
- заметка.

### Отдельно

- статус-кнопка справа.

## Responsive-правило для карточки

### Desktop

Внутренняя сетка карточки — 2 колонки:

- левая колонка: дата / работа / культура;
- правая колонка: препараты / заметка.

### Tablet

Та же схема, но уже с более плотной сеткой.

### Mobile

Одна колонка:

- статус;
- дата;
- работа;
- культура;
- препараты;
- заметка.

## Поведение календарных плиток

Плитки дат не фильтруют данные.  
Они должны работать как навигация по уже отрисованной общей ленте.

Правило:

- если у даты есть записи, плитка плавно скроллит ленту к этой дате;
- если у даты записей нет, показывается пустое состояние:
  - `На <дата> работы не назначены`

### Цвет плитки

Фон плитки должен отражать статус события:

- выполнено -> зеленый;
- запланировано -> синий;
- пропущено -> красный.

## Групповые задания

Если пользователь выбирает:

- несколько групп;
- несколько культур;
- несколько работ;

то система не должна рисовать отдельную карточку на каждую комбинацию.

Нужно:

- хранить связанные задачи в одном batch;
- отображать их в одной карточке;
- редактировать и удалять их как один связанный набор.

## Архитектурная цель следующего этапа

Нужно дожать приложение до структуры, где:

- все справочники едины;
- все формы используют один шаблон;
- все multi-select поля используют один компонент;
- вся лента использует один рендер-контур;
- все статусы живут на одном системном уровне;
- batch-логика вынесена в отдельный слой, а не размазана по обработчикам.

## Файлы, которые уже являются центром системы

- `index.html` — каркас приложения;
- `src/app.js` — UI, рендер, формы, dropdown-механики;
- `src/calendar.js` — работа с заданиями, статусами, batch-логикой;
- `src/storage.js` — локальное хранение состояния;
- `src/sample-data.js` — стартовые данные;
- `src/styles.css` — layout и визуальная система.

## Практическая цель на следующий этап

Следующий этап — не просто “подкручивать экран”, а собрать нормальную внутреннюю структуру:

1. единый `multi-picker` компонент;
2. единый `work-form` компонент;
3. единый `timeline-card` компонент;
4. единый слой `status + batch + repeat`;
5. после этого — чистка UI и дальнейшее превращение в полноценное приложение.
